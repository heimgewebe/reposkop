# Steuerboard → Reposkop architecture audit

Date: 2026-07-24. Baseline: `28f9660f5e3237cf469826800e69ded85a9b40aa`.

## Thesis

The useful core is a deterministic repository observation and readiness-derivation library. The old name and most historical surface area imply a control plane that the normative authority boundary explicitly denies.

## Counterthesis

Deleting the repository entirely would remove tested falsification, source-binding, freshness and explanation logic and would force those concerns into Grabowski or Leitstand. That would reduce separation and make operator effects harder to review.

## Decision

Keep a sharply reduced standalone library under the name **Reposkop**. It recognizes and explains. Grabowski protects, archives, removes and otherwise acts.

## Baseline findings

- Main was clean and matched `origin/main` at the audited baseline.
- No open Steuerboard pull request existed.
- The package contained 64 files and 21,238 lines; tests contained 164 files and 85,867 lines.
- There were 41 schemas, 259 example files and 32 documentation files.
- The normative boundary was observation-only, while the masterplan and code still retained action, approval, execution, runbook, host-gate and UI concepts.
- The host baseline ran 1,453 tests: 1,431 passed and 22 Runbook/Heimserver tests failed because a foreign `/tmp/.git` marker made `/tmp` appear to be a repository worktree. The failure did not affect the observation core and demonstrated avoidable coupling to host/runbook concerns.
- A previous global branch-drift run took roughly 34 seconds over 1,134 contexts. Global counts did not map reliably to target-specific action safety.

## Added contracts

- explicit checkout roles;
- lifecycle evidence envelope with source authority, digest and freshness;
- target/evidence subject binding;
- non-authoritative projection states;
- explicit `effect_authorized: false` on reports;
- bounded artifact size and explicit inventory target count;
- staged consumer and repository rename plan;
- event-bound automation policy.

## Alternative axis: library versus embedded Grabowski module

Embedding everything in Grabowski would reduce repository count, but it would also couple pure observation logic to the executor release cycle and weaken independent schema/falsification tests. A small library remains justified as long as it has no daemon, state store, UI or effect path.

## Risks

- Private consumers may import removed historical Python modules despite the earlier consumer scan.
- Repository rename can break publication identities and local remotes if performed before consumer cutover.
- Role heuristics can be wrong; explicit source-bound roles therefore take precedence and unknown cases remain inconclusive.
- Supplied lifecycle evidence can omit a blocker; Reposkop reports never authorize effects.

## Automation conclusion

Automate only event-bound target reports, post-lifecycle readbacks and digest-deduplicated Leitstand publication. Reject a daemon, global mandatory gate, unconditional scheduled fleet scan and cleanup executor.
